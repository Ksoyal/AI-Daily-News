# Gemini 晨报任务稳定性修复设计

## 目标

恢复每日晨报的稳定生成，并把一次工作流运行产生的 Gemini 请求数限制在可控范围内，避免服务过载时由重复重试进一步耗尽免费额度。

## 已确认范围

- 默认模型从 `gemini-3.7-flash` 恢复为此前连续成功运行的 `gemini-3.6-flash`。
- OpenAI SDK 客户端显式设置 `max_retries=0`，关闭 SDK 内部的隐式重试。
- 保留应用现有的 3 次指数退避，等待时间仍为 8、16、32 秒；加上首次请求后，单次晨报最多发送 4 个模型请求。
- 不增加 Gemini 与 OpenRouter 之间的自动跨供应商回退，避免本次修复扩大到多供应商路由和配置设计。
- 不改变 RSS 抓取、晨报提示词、Notion 发布、通知和工作流触发逻辑。

## 执行流程

`main.py` 继续调用 `generate_report()`。`generate_report()` 创建禁用内部重试的 OpenAI 兼容客户端，并通过现有外层循环处理 `RateLimitError`、连接错误和服务端错误。成功响应沿用现有解析与发布流程；4 次请求均失败时，保留当前异常上抛和失败通知行为。

## 测试与验证

1. 先增加回归测试，证明客户端没有显式关闭 SDK 重试时测试失败。
2. 测试客户端以 `max_retries=0` 创建，防止以后重新出现双层重试。
3. 测试默认模型为 `gemini-3.6-flash`，并保留环境变量可覆盖默认模型的现有行为。
4. 运行相关测试，再运行完整 `python -m pytest -q`。
5. 检查 Git 差异仅包含模型默认值、重试参数、测试和本设计文档。
6. 手动触发一次 `AI Daily News` 工作流并等待完成；验收标准是测试通过、生成与发布步骤成功，日志中的模型请求不再出现 SDK 内部重复重试。

## 非目标与回滚

本次不解决 GitHub cron 延迟问题，也不调整 Gemini 账户配额。若 `gemini-3.6-flash` 当前仍不可用，工作流会按原有方式失败并通知；届时再单独设计备用模型或跨供应商回退。代码回滚只需恢复模型默认值和客户端重试参数，不涉及数据迁移。
