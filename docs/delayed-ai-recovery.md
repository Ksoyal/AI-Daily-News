# Gemini 暂时故障的延迟恢复

2026-10-07 和 2026-10-09 的晨报在 Gemini 503 高负载错误后，原有的 8、16、32 秒重试全部失败。新的等待间隔为 **60、300、900 秒**，分别在前一次失败后计时。没有请求耗时的情况下，四次请求约在第 0、1、6、21 分钟发出。

- 每次运行仍最多调用模型 4 次；OpenAI SDK 内部重试保持关闭。
- 只重试现有的瞬时错误类别：限流、连接/超时和服务端错误。认证、请求参数错误和无效/空响应立即失败。
- 重试复用同一批 RSS、上下文、模型和提示词，不改变选题、编辑结构或核心话题规则，不跨供应商回退。
- 等待发生在生成步骤内，Notion 发布和 Server酱推送不在重试循环内。恢复后只发布一次、发送一次成功通知；耗尽重试后不发布，只发送一次失败通知。
- 工作流继续使用 `daily-run` concurrency 组串行处理手动、定时和 dispatch 触发；自动运行继续通过当日成功记录守卫去重，Notion 发布前仍检查当日页面。

## 时间预算与边界

默认 180 秒请求超时下，模型步骤名义预算为 `4 × 180 + 60 + 300 + 900 = 1980` 秒，即 33 分钟。工作流超时增至 60 分钟，留出 27 分钟给依赖安装、测试、RSS fallback 与 Notion 发布。SDK 的 HTTP timeout 按网络阶段/读取无活动时间计时，33 分钟不是严格墙钟上限，60 分钟的工作流超时才是运行硬上限。自定义 `AI_TIMEOUT` 时必须重新核算工作流超时；供应商持续故障或其他步骤超时仍可能导致失败。

这是**同一次运行内的延迟重试**，不是新增下午补跑计划，也不保证当日必定恢复。保留既有触发方式和 Notion 幂等检查，不修改凭据、权限或数据库。此改动不解决 Notion 写入响应丢失、部分页面写入失败等既有发布边界。

测试使用模拟 API 和模拟 sleep，不会生成实际日报或发送推送。合并前仅运行单元测试 CI；生产验证需要另行明确授权。
